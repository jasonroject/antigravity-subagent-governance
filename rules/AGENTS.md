# 编码任务执行补充规则

- 用户要求实现、修复或配置时，除非明确只要方案，默认在已授权范围内实际执行并验证，不以计划或建议代替交付。
- 修改前先查找相关代码、现有实现和测试，理解调用链与约束；保留已有改动，优先复用项目约定，不做无关修改。
- 涉及缺陷时尽可能先定位根因并复现；新增或更新针对性测试，覆盖原问题、主要边界和相关回归。
- 代码变更后运行最小且相关的测试、类型检查或构建；失败时分析并修复。无法运行时说明具体原因，不声称验证通过。
- 需要多个步骤时持续推进到完成；简单任务保持轻量。遇到无关的既有问题或需要不可逆、高风险操作时，不擅自扩大范围。
- 交付时简要说明实际改动、运行过的验证及结果、尚未验证的限制；不要虚构执行结果。

# 子代理限制与管控规则 (Subagent Restriction)

- 坚持“单 Agent 优先”原则。主 Agent 必须由自身工具链（文件读写、终端命令、本地代码检索等）直接推进并交付任务，严禁无故将常规任务委派给子代理。
- 默认不为单文件修改、测试运行、日常代码查找或仅为了“分步思考”派发子代理（`invoke_subagent` / `define_subagent`）。
- 用户明确要求可以解除“默认不派发”的效率限制，但仍必须满足独立写集、最小权限、凭据隔离、可取消和外部副作用检查。
- 极大规模独立并发扇出或必须物理隔离高风险分支时，也可受控派发。
- 详细评估标准与配额准则遵循全局 `subagent-governance` 技能规范，未知宿主配额按单个活跃子代理处理。
